## 1. 一句话结论

**核心链路已闭环，代码侧可以定版。**（V2.2：两库全接入 65,124 首、论证生成补齐；见 §8–§9）

剩余项分三类——**要外部数据的、要人工的、数据本身不支持的**，
三类都已如实标注，没有一项靠估算或编数填上。

定版的含义是：**不再新增功能**，只做部署复现、演示排练与现场核对（§5）。
继续改代码的边际收益已经低于部署演练的收益。

## 4. 我认为**不该**再做的

- **追 C5 整段逐字**：官方判分规则写明语义归类不判对错、只判变化值与方向，
  用模型猜金标那两句语义引文既不加分又冒编造风险。现状：每段给 3 条可定位候选，不硬凑。
- **把「无法判定」硬填成某个答案**：修正表覆盖不了的差异是口径固有限制，继续压数字只能靠编。
- **为凑门禁而估数**：A3 的人工一致率、情感基准的人工抽检，一律留空。
- **扩到多用户 / 写回 / 向量库**：分册 C §12.3 明确列为不做，理由成立。
- **领域微调**：无标注语料、无算力窗口（分册 A §A6）。
- **继续加功能**：本版体检后，代码侧没有已知的「点了没反应」类缺陷；
  再加功能的收益低于把现有功能在目标机上跑一遍。

## 6. 本次体检查出的真 bug（已全部修掉）

前几轮的检查是「后端 + 静态检查 + 逐页看正文长度」，**验不出「点了没反应」**。
这次补了两个真浏览器脚本（`check_pages_interactive.py` 探针级、
`check_interactions.py` 真点击级），查出 5 个真 bug：

| # | 现象 | 根因 | 状态 |
|---|---|---|---|
| 1 | 单篇解析页作品列表**整个是空的** | `/api/works` 的 `page_size` 上限 100，而页面取 120 → 400 | 上限放宽到 200；前端加了上限保护；补回归用例 |
| 2 | 检索页点「显示更多」报错 | `/api/search` 的 `limit` 上限 100，而「显示更多」每次 +100 → 150 撞墙 | 上限放宽到 500；前端到上限即隐藏按钮 |
| 3 | `/api/works?tier=all` 显示「共 483 篇」 | `total = len(rows)`，同源层只取了几条，总数跟着被截断 | 用探针查真实总数；**跨层分页重写**（官方层在前、同源层按全局位置接排，不重复不漏） |
| 4 | 图谱「焦点可分享」失效，URL 里的 `focus` 留不住 | 初始化 effect 依赖 `load`→`setParams`，URL 一变就重跑 `load(initialFocus="")` → `setParams({})` 把 focus 清空 | 改为只首次挂载加载一次；实测点节点后 URL 带 focus、深链能直接打开 |
| 5 | `polyphone.py` 异常处理器引用了未导入的 `ApiError` | 漏导入 | 补导入（走到那条分支会 NameError，掩盖真实异常） |

另修：词牌归一后两处词牌口径不一致（1,898 vs 1,897）——统一到 `tune_norm.is_caption_like` 一处判定；
`/api/tunes/resolve` 官方层没有的词调（如「雨霖铃」）现在回落到同源层并标来源；
未使用的导入/变量清理 11 处（pyflakes 清零）。

## 8. V2.1 补记：语料扩容与韵脚补齐（2026-11-05 下午）

用户核对作品描述时指出「2639 位词人、58851 首词作」的数据底座，并追问「之前给的
那两个数据库里真的没有这么多词吗」。复查发现 **V2 初版的结论有一处实质遗漏**：

### 8.1 数据底座：之前只接了两个公开库的一部分

规划（`词律探微-总体规划V6.1.md` §11）与实测报告
（`docs/报告/Tier2同源验证报告V1.md` §2）写明，「两库」是官方题库 `参考资料`
字段列出的 **poetry-source** 与 **chinese-poetry**，规划目标为
「公开整理本去重后 5–6 万首」。但实际只接了 poetry-source 的清、宋两个朝代
（43,191 首），其余 7 个朝代与 chinese-poetry 的宋词分片都没进索引
（早期清理时还把后者当「冗余语料」删了）。官方 API 实测 `total=423`，
只发布 423 篇；本机也确实没有 1.8 GB 的 `qing_ci_voice.db`。

**已补**：poetry-source `source/词/` 下剩余 7 个朝代——明 3,608 / 元 5,004 /
唐 590 / 五代十国 547 / 金 919 / 隋 1 / 南北朝 9，共 **10,678 首**，
**全部自带 `*.pinyin.json`**（与清、宋同口径，不引入第四种声律口径）。
同源层 43,191 → **53,869 首**，加官方 423 共 **54,292 首**，
落回规划「5–6 万首」区间；同源词人 3,381 位、词调 2,227 个、体式 6,337 种。

新层为 **Tier 2c**（id 前缀 `t2c_`），标签「同源历代词（非官方口径）」；
`/api/works`、`/api/search`、`/api/meta` 均支持 `tier=2c`，
前端档位与作品选择器的计数**改为从 `/api/meta` 动态取**，不再写死数字。

**仍不接 chinese-poetry 宋词 22 片**（约 21,000 首）：那批数据没有拼音，
接进来要用今音另算声律、引入第四种口径，且与 poetry-source 宋词大量重复。
**58,851 首是赛方官方数据库规模，不是公开整理本规模**——按 V6.1 §11，
可以如实说「检索语料扩展至公开整理本 5–6 万首」，
不能说「已接入 58,851 首官方数据库」。

### 8.2 韵脚：从「做不了」改为「已实现，但划清边界」

榜题要求研究者路径输出「逐字平仄、四声、**韵脚**」，V2 初版记为缺位。
复查发现 `Ci_Word_Tune.json`（词林正韵字表）每个字都带 `rhyme`（如「第一部」），
所以「给句末字查韵部」完全可行——之前把「与词谱韵位对齐做不了」
误记成了「整个韵脚做不了」。

**已补**：`scripts/build_rhyme_index.py` 派生 `data/rhyme_index.json`
（5,037 字 / 20 个韵部，原始字表只在构建期用、不随交付分发）；
`core/rhyme.py` 给逐句结果加 `line_end{line_end_char, rhyme, rhyme_found, note}`；
`/api/parse`、`/api/works/{id}/chars`、`/api/works/{id}/lines` 三处输出，
解析新词页与单篇解析页逐句显示「句末字 X · 第 N 部」。

实测《雨霖铃》「骤雨初**歇**」「兰舟催**发**」都判到**第十八部**，正是押韵句。
查不到的字返回 `null` 并写明「字表未收录（不猜测）」。
每页都有 `rhyme_boundary` 说明：韵部只是字表提示，
**不是与词谱韵位的校勘结论，也不据此判定某句是否押韵**。

> 通过声律自动解析（逐字平仄、四声、句末字与《词林正韵》韵部提示）、
> 可溯源的声情智能问答、论证辅助生成、校订建议队列与知识图谱导航五大功能，
> 实现标注数据的智能检索、深度分析与交互研究。
> 面向研究者，输入库内或库外词作即输出逐字声律与韵部提示；
> 面向教学，问答与论证的每条结论都可回跳到事实卡与原句；
> 面向数据库建设，校订队列给出差异 → 建议 → 人工复核 → 幂等导出
> （官方 API 只读，写回由官方流程完成）。
> 声情部分只提供**标「未验证」的候选方向**与形式线索，不下情感判定结论；
> 同源层一律标注「非官方口径」，不与官方基准混算。
> 交付物为可独立部署、运行时零外网依赖的 Web 应用。
