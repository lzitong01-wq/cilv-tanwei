# 修改指南 · 从改代码到线上生效

> 回答一个问题：**我要改点东西，怎么让它出现在公网网址上？**
>
> 一句话：**在本机改 → 提交推送 → 发一个 Release → 服务器自动部署**（约 20–40 分钟）。

---

## 0. 先记住三件事

| 事 | 为什么 |
|---|---|
| **在本机改，不要在服务器上改** | 服务器上跑的是发布包的副本（不含 `.git`），改那边下次部署就被覆盖 |
| **改完要发 Release，服务器才会更新** | 部署代理只认 GitHub Release，不会自动拉 git 仓库 |
| **大文件走 LFS** | `app/data/*.sqlite3` 超 100 MB，GitHub 单文件硬限制 |

## 3. 几种常见改动的注意点

### 只改文案 / 措辞 → 改 `rules.json`
判类措辞、公式口径、C5 边界文本、越界词表都在这儿。改完**不用改代码**，但要重新打包。

### 改前端页面
- 字体子集要覆盖新出现的字：改了语料或题库后必须重跑 `scripts/build_fonts.py`（`tests/test_fonts.py` 会拦住）
- `release.sh` 里已自动跑 `npm run build`

### 改了语料 / 题库 → 要重建索引
```bash
python app/scripts/build_tier2_locator.py    # 重建 Tier 2 索引（165 MB，走 LFS）
python app/scripts/build_fonts.py            # 重建字体子集
```
> ⚠️ 重建 `tier2_locator.sqlite3` 会让仓库多存一份 165 MB。**只在语料真的变了时重建**。

## 4. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| `refusing to allow an OAuth App to create or update workflow` | token 缺 `workflow` scope | 正常，`.github/workflows/` 推不上去，用 `scripts/release.sh` 发版 |
| Release 资产上传返回 400 | 资产名含中文 | `release.sh` 已改成纯 ASCII，别改回去 |
| **服务器版本没更新，代理日志也没报错** | **GitHub API 配额耗尽**（未认证 60/小时） | 见下方 §5 |
| 服务器部署失败，日志 `Interactive authentication required` | sudoers 路径不全 | `systemctl` 的 `/bin` 与 `/usr/bin` 两个路径都要写 |
| 服务器部署静默失败（软链不切换） | `cilv-deploy` 无权写 `releases/` | `chown cilv:cilv-deploy releases; chmod 775` |
| 代理下载卡住、刷进度条 | 服务器连不上 `github.com`（只有 `api.github.com` 通） | 代理已改用 API 端点，别改回去 |
| 公网打不开 | 本机装了 Tailscale，域名被 fake-IP 劫持 | **换台没装 Tailscale 的机器打开**，或用 `http://100.97.100.2:8080` |
| `ssh` 弹账号选择框 | 凭据管理器有多条 `github.com` 条目 | 命令里带 username：`https://lzitong01-wq@github.com/...` |
| `ssh` 要点网页确认 | Tailscale SSH 会话票据过期 | 打开命令输出的 `https://login.tailscale.com/a/xxx` **并点确认按钮**（打开页面不算） |

## 5. 服务器上「部署没发生」时按这个顺序查

```bash
ssh 龙蜥 'cat /opt/cilv/.deploy-state'      # 1. FAIL_COUNT 非 0 = 连续失败已停手
ssh 龙蜥 'journalctl -u cilv-deploy-agent -n 20 -o cat'   # 2. 有没有「软链已切到」
ssh 龙蜥 'ls -ld /opt/cilv/releases /opt/cilv'            # 3. cilv-deploy 有没有写权限
ssh 龙蜥 'grep GITHUB_TOKEN /etc/cilv/deploy.env'         # 4. token 配了没
```

**FAIL_COUNT 满 3 会停止自动部署**（保护机制，避免网络抖动时无限重试）。恢复：

```bash
ssh 龙蜥 'printf "DEPLOYED_TAG=<当前版本>\nFAIL_COUNT=0\n" > /opt/cilv/.deploy-state'
```

**GITHUB_TOKEN 必须配**：GitHub API 未认证配额只有 60 次/小时，部署代理 5 分钟轮询一次，
几小时就耗尽；耗尽后代理会「静默跳过」（不报错、也不部署），非常难查。
配上 token 是 5000/小时。

## 6. 服务器目录与常用命令

```
/opt/cilv/
  current → releases/<tag>          软链，指向当前版本
  releases/<tag>/                   各版本并存（回滚用）
  bin/deploy-agent.sh               部署代理脚本
  .deploy-state                     记录已部署版本与连续失败次数
/etc/cilv/deploy.env                环境配置（GITHUB_REPO / GITHUB_TOKEN / 轮询间隔）
/etc/systemd/system/cilv.service              应用服务单元
/etc/systemd/system/cilv-deploy-agent.service  部署代理单元
/etc/sudoers.d/cilv-deploy          部署代理的重启权限白名单
```

```bash
ssh 龙蜥 'systemctl status cilv'                    # 服务状态
ssh 龙蜥 'journalctl -u cilv -f'                    # 实时日志
ssh 龙蜥 'systemctl restart cilv'                   # 重启
ssh 龙蜥 '/opt/cilv/bin/deploy-agent.sh --version'  # 已部署版本
```

**手动回滚**：

```bash
ssh 龙蜥 '
  ls -1t /opt/cilv/releases/ | head -3
  ln -sfn /opt/cilv/releases/<上一个tag> /opt/cilv/current
  systemctl restart cilv
'
```

## 7. 访问地址

### 三种方式，各自的可用条件

| 地址 | 形式 | 谁能用 | 前置条件 |
|---|---|---|---|
| `https://10.27.80.204/` | **IP + HTTPS** | 校园网 `10.27.x.x` 网段 | 自签证书，浏览器点「继续访问」 |
| `https://localhost-0.tail1fb5ab.ts.net/` | 域名 + HTTPS | **任何人** | 无。浏览器直接打开，证书可信 |
| `http://100.97.100.2:8080` | IP:端口 | 装了 Tailscale 的机器 | 装 Tailscale 并加入同一 tailnet |

**给评委用，首选第一个或第二个**：
- 第一个是**校园网 IP 形式**（与同网段其他队伍一致），需在 `10.27.x.x` 网段内
- 第二个不依赖校园网，任何网络都能开

### 为什么必须用 443 而不是 8080（实测结论，2026-11-05）

**校园网 ACL 只放行 80/443 两类标准端口。** 用同网段另一台机器做对照实验：

| | 80 | 443 | 8080 | 22 | 8000/9000 |
|---|---|---|---|---|---|
| 参照机 `10.27.80.205` | ● 通 | ● 通 | ✗ 超时 | ✗ 超时 | ✗ 超时 |
| 本机 `10.27.80.204` | ✗ 超时 | ✗ 超时 | ✗ 超时 | ✗ 超时 | ✗ 超时 |

参照机的 8080 同样超时 → **是校园网按端口放行，与机器无关**。

所以本服务在 8080 上跑（内部端口），**由服务自己在 443 上建 TLS 入口反代过去**，
结构与参照机一致（参照机是 nginx 挂 443 → 反代内部端口）。

### 443 入口怎么来的：服务启动时自举

`app/backend/core/edge.py` —— 服务启动时尝试在 443 建立 TLS 入口：

- 仅用 Python 标准库，**不依赖 nginx**（实测该机 nginx 装得上但服务起不来）
- 证书缺失 / 端口占用 / 绑定权限不足，各状态**如实记录**不掩盖
- **自举失败不影响主服务**：8080 照常提供
- 状态写进 `GET /api/health` 的 `deployment.edge` 字段，远程即可判断

一次性安装（已执行过，幂等）：

```bash
bash app/deploy/setup_tls_edge.sh          # 生成证书 + 放行防火墙 + 建入口
```

### 网段隔离的另一面（别再误判）

`10.28.x.x` 网段与 `10.27.x.x` 网段之间被隔离。开发机在 `10.28.185.51`，
从它测 `10.27.80.204` 的**任何端口**都超时——**这不是服务器配置问题**，
换个 `10.27.x.x` 网段的机器（如 `10.27.60.16`）就能正常 SSH。

> 判断可达性务必**区分 RST 与超时**：
> `ConnectionRefusedError` = 网络通、该端口无服务；`socket.timeout` = 被丢包（ACL/防火墙）。
> 用 bash `/dev/tcp` 只分「通/不通」会把两者混为一谈。

### Tailscale 通道偶发卡死的处理

现象：状态显示 `active; relay "xxx"` 但 `rx 0`，所有请求超时。
**解法：重启本机 Tailscale Windows 服务**（不需要管理员以外的任何操作）：

```powershell
Restart-Service Tailscale -Force
& "C:\Program Files\Tailscale\tailscale.exe" ping -c 3 100.97.100.2
# 期望输出：pong via <ip>:41641 in 3ms   ← direct 直连（几毫秒）
# 若显示 via DERP(xxx) in 2000ms+        ← 走了中继，仍能用但慢
```

**排查优先级**：优先用公网 HTTPS 通道确认服务器状态——它不依赖 Tailscale，
在 Tailscale 完全卡死时依然可用。

### 评审怎么核对「确实部署在服务器上」

打开 About 页的「部署与运行环境」区块，里面的**服务器主机名、进程 PID、
启动时刻、数据根目录、检索后端版本**全部由服务在运行时从 `/proc` 与实际路径读取，
不是写死的文案——换台机器跑就会显示另一台机器的信息。
