## 二、逐一调研

### 2.1 farion1231/cc-switch

#### 定位

> README.md（首段）：
> "CC Switch — The All-in-One Manager for Claude Code, Claude Desktop, Codex, Gemini CLI, Grok Build, OpenCode, OpenClaw, Hermes Agent, Pi, MiniMax Code, Kimi Code & Oh My Pi"

**解决的真问题**：AI 编程工具（Claude Code / Codex / Gemini CLI …）各自把模型配置写在自己的 JSON/TOML/YAML 里，切换 API 供应商要手改配置；MCP、Skills、Prompts 又要在每个工具里各维护一份。cc-switch 把「换供应商 / 统一 MCP、Skills、Prompts」收进一个桌面应用。

**目标用户**：同时使用多个 AI 编程 CLI 的开发者。

**规模与形态**：Tauri 2 + Rust 后端 + React 18 + TypeScript + SQLite；`package.json` 版本 `4.0.25`；`src-tauri/src/` 下最大文件 `codex_config.rs` 262 KB、`forwarder.rs` 356 KB。是一个体量不小的桌面产品。

#### 关键手法与出处表

| 关注点 | 具体实现 | 出处 |
|---|---|---|
| **模型路由 / 三种模式** | Direct（直连）、Routing（本机 `127.0.0.1:15721` 转发 + 协议转换 + 故障转移）、Aggregation（多供应商模型合并成一个模型列表，客户端 `/model` 选哪个就走哪家）。三者互斥 | `README.md`「Supported Features by Tool」表；`docs/user-manual/en/4-proxy/4.6-aggregation.md` |
| **适配层边界** | 协议转换集中在 `src-tauri/src/proxy/`，按 provider 拆到 `src-tauri/src/proxy/providers/`；整流器（rectifier）独立成文件：`thinking_rectifier.rs`、`thinking_budget_rectifier.rs`、`opaque_state_rectifier.rs`、`media_sanitizer.rs` | `src-tauri/src/proxy/` 目录树 |

| **「中立释放探测名额」** | `release_permit_neutral()`：整流器场景请求结果不应计入 Provider 健康度，但必须释放 HalfOpen 名额，否则 Provider 长时间进不了探测态 | `src-tauri/src/proxy/provider_router.rs` |
| **提示词管理** | 库 + 按应用投影：`prompt_file_path()` 映射到 CLAUDE.md / AGENTS.md / GEMINI.md / SOUL.md；`PromptService` 负责 upsert/enable/delete/sync_to_live/sync_all_to_live；`project_prompt_set_to_path()` 遇到多条同时启用时**按稳定顺序投影第一条并返回告警**；`validate_prompt_content()` 对 MCode 限 32 KiB；启用时先回填 live 文件内容并自动备份原始提示词 | `src-tauri/src/prompt_files.rs`；`src-tauri/src/services/prompt.rs` |

| **交互设计** | 系统托盘 + 托盘面板（`tray_panel.rs` 51 KB）+ 项目切换器（Projects）+ 深浅主题 + 原子写 + 自动备份 | `README.md`「System & Platform」段 |

#### 许可证与依赖

- **LICENSE**（SHA `d84c4f73`）：标准 MIT，`Copyright (c) 2025 Jason Young`。
- **依赖**：`package.json` 中 React 18、Tauri 2、zod 4、smol-toml 1.9、@codemirror/*、@dnd-kit、recharts、flexsearch；Rust 侧用 SQLite。无强制联网/付费 API 依赖（它是路由器，上游供应商另计）。模型元数据与价格会从 **models.dev** 拉取补全。
- **离线内网适配度**：**应用层面可以**（本地 SQLite + 本地代理），但 **目标平台不兼容**——README「System Requirements」写明 Linux 需 `x86_64 or ARM64 with glibc 2.35+ and WebKitGTK 4.1`，并直接注明 `RHEL / Rocky / Alma 8–9 are not supported yet`。Anolis OS 与 RHEL 系同源，属明确不支持区间。

#### 对我们的可直接借鉴点

1. **写入引擎**（`src-tauri/src/live/engine.rs`）——照着做：我们的题库/事实卡/配置落盘统一走 `plan → stage → 首写备份 → hash 比对 → rename`，断电与并发安全，且「首次写入前留原文件备份」正好覆盖「误改题库不可逆」的比赛场景。
2. **能力三态 + 精确白名单 + fail-open 的反面**（`src-tauri/src/model_capabilities.rs`）——照着做：把「qwen3.8-27b 合规 / step-3.7-flash 不合规」做成显式 capability 声明表，**未声明的组合落到 Unknown 而不是默认放行**（与 cc-switch 的 fail-open 方向相反，我们应 fail-closed）。特别注意它的教训：**不要让新后缀自动继承能力**（`glm-5.2v` 的例子）。
3. **提示词库 + 稳定顺序投影 + 单条启用 + 投影前自动备份**（`src-tauri/src/services/prompt.rs`）——照着做：我们四类 LLM 副功能（风格画像 / 风格对比 / 情感候选 / 检索扩展）不该是散落字符串，而应是「库 → 启用一条 → 投影到提示词 → 投影前备份」。多条同时启用时按稳定顺序取第一条并给出告警，这一条能直接消歧义。
4. **提示词体积上限**（`prompt_files.rs` 的 `validate_prompt_content`）——照着做：我们给 LLM 的模板加字节上限，防止 prompt 膨胀。

#### 必须避开

- **AGPL 传染？不适用**（它是 MIT），但**平台不兼容**：Tauri 2 桌面应用 + WebKitGTK 4.1 + glibc 2.35+，且 RHEL/Rocky/Alma 明确不支持 → Anolis OS 上跑不了，也没有 48h 内移植成 Web 服务的余量。
- **产品域不同**：它的核心是「篡改别家 CLI 的配置文件」，我们的核心是「研究助手 + 确定性引擎」。UI 交互、托盘、项目切换器全部无用。
- **不要照抄它的 fail-open 语义**：它的 Unknown→按支持处理是「宁可多发一次请求」。我们的事实闸门必须相反：无法归因的数字**一律拦截**。
- **不要引入 models.dev 联网依赖**：内网离线部署下价格/元数据补全必须全部预置。

### 2.2 lidge-jun/opencodex

#### 定位

> README.md：
> "opencodex is a lightweight local gateway between your coding tools and your model providers. It accepts the Responses, Chat Completions and Anthropic Messages APIs and translates each request into whatever your provider speaks"

**解决的真问题**：把 Codex / Claude Code / Claude Desktop / Grok Build 的请求统一收敛到一个本机网关，由网关做协议翻译、账号池路由、故障转移、限流与可观测。

**目标用户**：重度使用多家模型供应商、且要在多个编码 Agent 之间切换的开发者。

**形态与规模**：npm 包 `@bitkyc08/opencodex` v2.97.0，`engines.node >= 18`，自带 Bun 1.4.4 运行时；`src/` 下有 `adapters/`、`routing/`、`compatibilitiy`、`lab/`、`structure/` 等；`structure/INDEX.md` 67 KB、`structure/runtime.md` 168 KB、`structure/providers-and-adapters.md` 124 KB；`src/adapters/anthropic.ts` 89 KB。

#### 关键手法与出处表

| 关注点 | 具体实现 | 出处 |
|---|---|---|
| **模型路由（确定性打分）** | `evaluatePolicyProfile()`：候选按声明顺序打分，每项能力要求产出 `satisfied / unsatisfied / **unknown**` 三态；`unknown` 的处置由 profile 的 `unknownEvidence` 决定（`exclude` / `penalize` / `allow`）。权重：health、quota、cost、latency 四个显式权重之和不超过 1，余下给 `configuredPriority`；compatibility 是**纯惩罚项**，不加分也不改声明顺序 | `src/routing/evaluator.ts` |
| **有界决策轨迹** | `buildRouteDecisionTrace()`：候选 ≤ 8、每候选排除理由 ≤ 16、要求 ≤ 16、字符串 ≤ 128 字符、**序列化后 ≤ 16 KiB**；`enforceByteBudget()` 分阶段降级（先丢 detail，再丢 exclusions，再折半候选）；`truncated` 标记哪些上限生效。`normalizeRouteDecisionTrace()` 反序列化时**按白名单逐字段校验**，非法证据整块丢弃而非污染 DTO | `src/routing/trace.ts` |
| **兼容清单（本项目最值钱的一处）** | `compatibilityManifestIssues()` 校验一个版本化清单：<br>① `subject` 精确锁定主体（providerId + **规范化绝对 baseUrl** + adapterId + authMode + inboundProtocol + upstreamProtocol + modelIds）；<br>② `claims[]` 每条一个 feature，disposition ∈ `passthrough / translated / degraded / unsupported`，**非 passthrough 必须写 limitation**；<br>③ 每条 claim 必须挂 `evidence`（`kind` ∈ `fixture / lab-scenario`，fixture 类还要给 `assertionIds`）；<br>④ `defineCompatibilityManifest()` 校验不过直接 `throw TypeError`，过了则 `deepFreeze` | `src/compatibility/manifest.ts` |

| **适配层边界** | `ADAPTER_REGISTRY`：每个适配器声明 `wire`（11 种线路）+ `mutation`（`codex-owned` / `codex-owned-with-gated-native-fallback`），或声明 `contractParent` 继承语义契约；`effectiveAdapterContract()` 沿父链上溯并**检测环**（抛 `Adapter contract cycle detected`）；`createRegisteredAdapter()` 统一给非 `openai-responses` 线路套 `withInputMediaGuard`，并把 tier 观测元数据挂到请求上 | `src/adapters/registry.ts` |
| **适配器接口** | `ProviderAdapter`：`buildRequest`（可异步，因为要解析短期凭证）/ `parseStream`（AsyncGenerator）/ `parseResponse` / `runTurn`（自持传输的适配器）/ `localTerminal`（**在构造请求前**判定本轮无需上游推理，直接本地构造完成响应）/ `formatErrorBody`（必须纯函数且完全脱敏） | `src/adapters/base.ts` |
| **结构化输出的「可证明」子集** | `satisfiesOpenAiStrictSchema()`：逐关键字白名单判定一个 JSON Schema 能否在 strict 模式下保持对象契约；**遇到未知关键字 fail closed**（不维护不完整的黑名单）；注释直言：改写 `required` 去迎合 strict 会静默改变调用方的契约，唯一诚实的回答是「不再声称 strict」。另有 `OPENAI_FINE_TUNED_UNSUPPORTED_KEYWORDS`（微调模型子集更窄） | `src/adapters/anthropic-output-schema.ts` |

| **配置写入** | 首次发布用 `publishInitialConfigNoReplace()`（临时文件 + 硬链接，不覆盖）；日常更新用 `persistConfigUnlocked()` 在 `withConfigMutationLockSync()` 锁内原子替换；带 config generation 计数防并发覆盖 | `src/config.ts`；`src/config/atomic-write.ts`（由 `config.ts` 导出） |

### 2.3 yetone/magpie

#### 定位

> README.zh-CN.md：
> "所有 Agent 的模型，一处搞定。… 在菜单栏一点就能切换。所有 Agent 共用一个本地网关，额度用完时，它会悄悄切到你的下一个账号。"

**解决的真问题**：多个 Agent CLI 各自配置模型、订阅账号不能跨 Agent 用、额度用尽即中断。magpie 用一个本地网关（`127.0.0.1:3425`）统一承接 OpenAI Chat / OpenAI Responses / Anthropic Messages / Gemini 四种协议并互相翻译，再把「路由组」暴露给 Agent 选。

#### 对我们的可直接借鉴点

1. **「规则 + 为什么 + 证据 + 次数」的评审知识库**（`LESSONS.md`）：照着做，我们项目内的 `docs/decisions.md` 或 ADR 集应采用同一格式。直接可用的条目：
   - *A failed read, parse or hash means "unknown"* → 引擎读不到数据时返回 unknown，绝不返回默认值（我们的确定性引擎的黄金规则之一）。
   - *A test named for a guarantee fails when it breaks* → 闸门测试必须先在旧代码/故意违规样本上验证为红，否则测试无效。
   - *A fix reaches every sibling of the bug* → 改一处判定逻辑要同步所有同类出口（分句、平仄计数、比例、变幅、极差、选句各出口）。
   - *Never let the default override a value the user set* → 默认配置不得覆盖用户显式设置（我们的引擎参数/阈值）。
   - *Nothing that can block runs under a lock its reader needs* → 闸门校验不得在读锁内阻塞。
2. **钩子超时 + fail-open 的明确语义**（`internal/middleware/middleware.go`）：照着做，我们的 LLM 副功能调用要有硬超时（建议 8–15s），超时时**引擎结果照常输出、LLM 部分留空并标注「未验证/未生成」**，绝不让 LLM 拖垮引擎路径。这与「LLM 是副功能」的定位完全一致。
3. **「每次尝试从原始体重新开始」**（`triedOn()` 的语义）：若我们做多候选重试（先 qwen 失败再试 step），每次重试必须基于**引擎原始事实卡**重建请求，而不是继承前一次被改写的体。
4. **「不可证明就不发」**（`internal/masking/masking.go` 的 503 拦截）：脱敏失败时宁可拒绝发送，也不原样发送。我们的事实闸门同理：无法归因的数字**宁可丢弃该句**，不原样放行。
5. **占位符稳定性原则**：masking 强调「同一个值每次的占位符都一样，对话上下文、提示词缓存和 thinking 签名都不受影响」。我们的「未验证」标注也应稳定、不引入随机串，方便评测比对。
6. **Prompt 里不许出现产品名**（`LESSONS.md`：「Text magpie adds to a prompt that goes to a vendor names neither magpie nor the vendor's limits」）→ 我们给 LLM 的提示词里**不要出现产品名与限制说明**，避免污染风格画像输出。

- **许可可用但协作不可用**：README.zh-CN.md 明确「本仓库不接受 Pull Request，只有维护者能提交」。我们只能读，不能提交修改，也不能指望上游配合。

2. **平仄变体块**（`_check_tone()` 的 `List[List[Dict]]`）：一个位置有多种合法谱式时，用嵌套列表表达变体组，逐组试并展平选中者。这比「单一线性模板」更适合清代词谱的实际情况。
3. **「多音字不猜」**（`_get_char_tones()` 返回 `{'A'}`）：字有多个韵部或多个平仄时，**不静默取第一个**，而是标为「可平可仄」或保留多值。对应我们的「多值保留」原则。

5. **只读 SQLite + `schema_version` 校验**（`dict_db.py` 的 `check_health()`）：我们的三层数据（Tier0/Tier1/Tier2）可落成只读 SQLite，启动时校验 `manifest.schema_version == 1`，不匹配直接判定不可用而非静默降级。

**读表结论**：
- **opencodex 是唯一在「输出校验」与「评测」两栏同时拿到 ● 的项目**，且这两栏恰是我们的核心（四道闸门 + 证据链 + 1000 题回归）。
- **「离线部署」一栏唯一与我们目标完全匹配的是 chinese_word_rhyme**，而它的价值恰好在最不需要授权的地方（数据结构设计），不在需要授权的地方（词谱数据）。
- **fangcun 与 chinese-poetry-analyzer 在「许可证」一栏都是 ✖**，两者都提供了大量好思路，但都必须「读思路、自写代码、另找数据」。
- **「评测」一栏暴露了最危险的现状**：两个中文诗词项目一个无测试、一个停滞；我们的 700+300 题评测体系是资产，必须用 opencodex 的**负向对照**把它从「没写坏」升级为「证明有效」。
