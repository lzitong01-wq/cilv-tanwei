# 知识库只读，校订闭环止于导出

官方《开放知识库 API》文档明确：该知识接口**不支持写入方法**（返回 405），且"标注写入"不在开放范围内。因此本项目的校订闭环终点定为**导出给官方回写流程**；产品内不做直接回写生产库的功能，只提供可核验的导出与幂等保证。

## 为什么

这不是保守取舍，而是接口契约的直接约束。此前规划把"直接写回源库"写成"L4，需授权 + 二次确认"，隐含了存在写接口；实际上只有只读 API，写回必须走官方流程。在没有写接口的前提下设计"写回"功能，只会产生一个必然失败的按钮。

## 怎么落地

- 闭环层级改为：L0 发现 → L1 建议 → L2 人工复核 → L3 幂等导出（**本轮终点**）；原 L4 改为"官方回写（不在本系统内实现）"；
- 导出文件必须包含：作品 ID、行号与原值、系统建议值、依据与证据 ID、置信状态、规则版本，便于官方复核；
- 导出幂等：同一条差异重复导出不产生重复条目；
- 系统任何路径都不得对官方库发起写入请求（连试探性 POST 都不做）。

## 后果

- 板块 H 的"闭环更新"在对外表述上改为"**闭环到导出**"，并说明最终写回由官方流程完成，避免夸大能力；
- 新增不变量 INV-WB-11 的执行细则：任何写请求视为缺陷，由 `sidecar`/`eval` 侧的负向用例守住；
- 评审若追问"能否自动更新标注"，答案是当前 API 不支持，我们已做到接口允许的极限。
